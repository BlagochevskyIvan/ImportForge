# ImportForge

Учебный backend для импорта CSV от поставщиков. Текущий этап — авторизация,
защищённый CRUD поставщиков, гибкие конфигурации CSV, загрузка и история запусков. PostgreSQL работает
в Docker, Python — локально.

## Что уже работает

- Асинхронный SQLAlchemy и контекстный менеджер сессий.
- Миграции Alembic: установка с пустой базы и обновление предыдущей версии проекта.
- Схемы создания, обновления и ответа для пользователей, поставщиков и CSV-конфига.
- CRUD с одной переданной сессией; проверка владельца поставщика и конфига.
- Хеширование bcrypt; функции JWT RS256 с ограниченным временем жизни.
- Регистрация, вход, профиль текущего пользователя и защищённые операции с поставщиками.
- Ruff и тесты схем, паролей, CRUD и миграций на настоящем PostgreSQL.

HTTP-маршруты: `POST /users/auth/register`, `POST /users/auth/login`, `GET /users/me`,
`POST /suppliers`, `GET /suppliers`, `GET /suppliers/{supplier_id}` и
`PATCH /suppliers/{supplier_id}`. Операции с поставщиками проверяют владельца.

Конфигурации CSV именованные и версионируемые.
`GET|PUT|POST|DELETE /suppliers/{supplier_id}/config` сохраняют совместимость с прежними маршрутами;
`GET /suppliers/{supplier_id}/configs` возвращает сохранённые версии с пагинацией.
`PUT` принимает `name` и `config_data`, добавляет изменённую версию с новым ID;
повтор тех же настроек для того же имени возвращает существующую последнюю версию.
`POST` всегда создаёт версию. Имена — подписи, ID однозначно определяет версию.
Все операции проверяют владельца. `DELETE` удаляет все версии поставщика,
но сохраняет снимки и результаты уже созданных запусков.

В `config_data.columns` задаётся упорядоченный список произвольных колонок:
`source`, `target`, `type` (`text`, `integer`, `decimal`), `required`, `trim`,
`min_value`, `max_value`. Глобально обязательных `sku/name/price` нет.
Старый `column_mapping` читается адаптером совместимости; новые ответы и снимки
используют формат `schema_version: 2`. Старая тройка сохраняет прежние правила
только при чтении старого формата.

`POST /imports` сохраняет CSV с `supplier_id` независимо от наличия конфигурации.
При наличии текущих настроек оставляет их копию на файле для совместимости.
`POST /imports/{file_id}/runs` принимает `{ "config_id": 123 }`, создаёт отдельный
`ImportRun` со снимком выбранных настроек и выполняет обработку синхронно (`201`).
Конфиг должен принадлежать тому же поставщику. История и конкретный запуск:
`GET /imports/{file_id}/runs` и `GET /imports/{file_id}/runs/{run_id}`.
Скачивание конкретного результата: `GET /imports/{file_id}/download?kind=result&run_id=...`.
Прежний `/process` возвращает последний успешный результат без новой обработки,
если тело запроса не выбирает конфигурацию; явный `config_id` создаёт новый запуск.
После неудачи повтор `/process` также создаёт новый запуск.

На странице поставщика доступны произвольные колонки и правила, выбор сохранённой
версии, загрузка исходника, новые запуски и история скачивания. Ошибки отдельных
строк попадают в отчёт, ошибки структуры файла завершают запуск с `failed`.
Обработка по-прежнему выполняется внутри HTTP-запроса с выносом блокирующей работы
в поток. Примените `make migrate` и перезапустите API и интерфейс.
Подробный разбор подготовительного этапа, полей и границ:
[IMPORT_PREPARATION.md](IMPORT_PREPARATION.md).

Refresh/logout реализованы в `/users/auth/refresh` и `/users/auth/logout`.
Маршрут `/` у FastAPI не объявлен, поэтому возвращает 404; стартовый экран обслуживает Next.js.

## Первый запуск на macOS

Команды выполняются из корня репозитория. Нужны Python 3.12+ и Docker Desktop;
проверено на Python 3.14.2 и PostgreSQL 17.

```bash
cd /Users/ivanblagocevskij/Programs/Projects/ImportForge
open -a Docker
make install
make env
make db-up
make keys
make migrate
make migration-check
make run
```

Перед `make db-up` дождись готовности Docker Desktop. `make install` создаёт `.venv`
и устанавливает зависимости. Существующий `.env` команда `make env` не перезаписывает.
`make keys` создаёт локальную RSA-пару в `certs/`, не заменяя существующие ключи.
Существующая пара проверяется на корректность и совпадение. Приватный ключ получает
права 600; каталог исключён из Git. Прежняя вторая пара сохранена в `certs/legacy/`
и приложением не используется.

В другом терминале проверь:

```bash
curl -f http://127.0.0.1:8000/openapi.json
```

Открой Swagger: <http://127.0.0.1:8000/docs>.
На старте приложение выполняет `SELECT 1`; недоступная БД останавливает запуск.

Без Makefile те же действия запуска приложения:

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
docker compose up -d --wait postgres
python -m scripts.generate_keys
python -m alembic upgrade head
python -m alembic check
python -m uvicorn src.main:app --reload
```

`requirements.txt` содержит зависимости приложения и инструменты разработки:
pytest, httpx и Ruff. Версии прямых зависимостей зафиксированы по проверенному
окружению; это не полный lock-файл всех транзитивных зависимостей.

## Настройки

Скопируй `.env.example` в `.env` через `make env` и при необходимости измени значения:

| Переменная | Назначение |
| --- | --- |
| `DB_USER`, `DB_PASS`, `DB_NAME` | Первичная настройка PostgreSQL-контейнера |
| `DATABASE_URL` | Соединение SQLAlchemy, обязательно `postgresql+asyncpg://...` |
| `TOKEN_EXPIRATION_MINUTES` | Положительный срок access JWT в минутах, по умолчанию 15 |
| `SQL_ECHO` | Вывод SQL; по умолчанию выключен, значения параметров скрыты |
| `TEST_DATABASE_URL` | Отдельная тестовая база на порту 5433 |

Пароли в примере предназначены для локальной разработки. Порты PostgreSQL привязаны
к `127.0.0.1`. Изменение `DB_PASS` не меняет пароль в уже созданном Docker volume.
Если пароль содержит специальные символы URL, закодируй их в `DATABASE_URL`.

## Миграции

```bash
make migrate
make migration-check
.venv/bin/python -m alembic current
```

Используй Alembic как единственный штатный способ менять структуру базы.
`python -m src.db.database` теперь выводит подсказку использовать `make migrate`.

Ранее первая ревизия была пустой и предполагала вручную созданную таблицу suppliers.
Теперь она создаёт эту исходную таблицу, поэтому вся цепочка работает с пустой БД.
Для базы, уже отмеченной ревизией `b54de5027f26`, эта первая ревизия заново не выполняется.
Новая ревизия `c84c8b7d1a20` добавляет типы, владельца и ограничения CRUD.

Ревизия `e91b7c2a4f60` заменяет уникальный индекс `import_configs.supplier_id` обычным,
сохраняя существующие конфиги и снимки файлов. Применяется через `make migrate`.
Откат этой ревизии останавливается, если у поставщика несколько версий: миграция
не удаляет историю автоматически ради восстановления уникальности.

Миграция не угадывает владельцев старых поставщиков: если в старой схеме есть
поставщики или конфиги, она останавливается до изменений. В этом случае нужен
отдельный план назначения владельцев и переноса конфигов. Не удаляй данные и не
используй `alembic stamp head`, чтобы обойти это условие. Старые числовые Unix timestamp
в `users.created_at` преобразуются в дату с часовым поясом; email нормализуется в нижний
регистр. Конфликт email или некорректное время приводят к откату миграции.

После нового изменения моделей:

```bash
.venv/bin/python -m alembic revision --autogenerate -m "describe schema change"
# Сначала прочитай upgrade() и downgrade() в созданном файле.
make migrate
make migration-check
```

Для просмотра реальных таблиц:

```bash
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\dt"'
```

## Форматирование и проверки

```bash
make lint
make format
make test-unit
make test-db-up
make test
```

- `make lint`: правила Ruff и проверка формата без изменения файлов.
- `make format`: форматирование файлов, не исправление бизнес-логики.
- `.venv/bin/ruff check . --fix`: исправления линтера, после которых нужно посмотреть diff.
- `make test-unit`: схемы, пароли, JWT и генерация ключей, без подключения к PostgreSQL.
- `make test`: все проверки; отсутствие тестовой БД считается ошибкой, а не молчаливым пропуском.

Тестовый PostgreSQL — отдельный сервис `postgres_test` с профилем `test`, портом 5433
и временным хранилищем. Обычный `docker compose up -d` его не запускает.
Тестовая база должна называться `test_...` и отличаться от рабочей. Тесты применяют
реальные миграции. CRUD-тесты используют реальные SQL-запросы и откат внешней транзакции.

```bash
make test-db-stop
make db-stop
```

Остановка рабочего PostgreSQL сохраняет его данные в volume. Данные тестового сервиса
временные. Полный список команд: `make help`.

## Где продолжать разработку

| Каталог | Ответственность |
| --- | --- |
| `src/schemas/` | Pydantic: допустимые входные данные и публичные ответы |
| `src/db/models.py` | SQLAlchemy: таблицы, типы, внешние ключи и ограничения |
| `src/db/*_crud.py` | Чтение и изменение данных через переданную сессию |
| `src/db/database.py` | Engine, фабрика сессий, `asynccontextmanager` |
| `src/auth/` | Хеширование и JWT-функции |
| `src/api/routers/` | HTTP-обработчики и преобразование ошибок |
| `src/api/dependencies.py` | Bearer-аутентификация и получение текущего пользователя |
| `migrations/` | Версионирование схемы БД |
| `certs/` | Локальные RSA-ключи; содержимое исключено из Git |
| `tests/` | Проверки контрактов и работы PostgreSQL |

Подробное объяснение решений, примеры вызова каждой группы CRUD и план подключения
роутеров: [Как устроен подготовленный каркас](docs/backend_basics.md).
